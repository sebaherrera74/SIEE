Volver a la FPGA

Después de un tiempo sin trabajar con la Arty Z7-10, decidí volver a ponerla en funcionamiento porque quiero incorporarla nuevamente al trabajo del laboratorio.

La placa no era completamente nueva para mí: ya había trabajado anteriormente con ella, pero había pasado bastante tiempo y algunas cosas había que volver a recordarlas. Así que este proyecto terminó siendo, en parte, un reencuentro con la FPGA y, en parte, una oportunidad para ordenar y documentar lo que estaba haciendo.

Para empezar decidí ir por algo relativamente sencillo: generar una señal PWM, controlar el duty cycle mediante botones y comprobar la señal directamente sobre el hardware con un osciloscopio.

La idea parecía bastante simple.

Spoiler: siempre parece simple al principio. 😄

El objetivo inicial no era hacer un proyecto especialmente sofisticado, sino volver a familiarizarme con el flujo completo de trabajo: VHDL → simulación → síntesis → implementación → bitstream → hardware real.

Y, de paso, dejar documentado el proceso para que la próxima vez que vuelva a mirar esta placa no tenga que empezar preguntándome nuevamente: "¿Cómo era esto?".

Como suele ocurrir en estos casos, uno empieza pensando: "Bueno, tampoco debe ser tan complicado. Hago un contador, genero una señal PWM y listo."

Spoiler: no era tan simple.

El objetivo inicial era bastante modesto: generar una señal PWM, controlar el duty cycle mediante unos botones y finalmente comprobar que la señal apareciera en un pin físico de la placa.

Lo que no había calculado era que para conseguirlo iba a tener que aprender VHDL, simulación, síntesis, implementación, constraints, bitstreams, Vivado y, sobre todo, la diferencia entre "el código funciona" y "la FPGA hace lo que yo creo que le dije que hiciera".

Así que decidí hacer algo todavía más peligroso: documentar el aprendizaje mientras lo estaba aprendiendo.

La placa

El proyecto fue realizado utilizando una Arty Z7-10, basada en la familia Zynq-7000.

Una de las primeras cosas que tuve que tener en cuenta fue el reloj de la placa. La Arty Z7 utiliza un reloj de 125 MHz.

Eso significa que cada ciclo de reloj dura: 

125 MHz → 8 ns por ciclo

Este dato parece bastante inocente hasta que uno empieza a hacer las cuentas para generar frecuencias más bajas.

Primera lección: si el reloj es de 125 MHz, las cuentas tienen que hacerse con 125 MHz.

Primer objetivo: generar PWM

El primer PWM fue diseñado para trabajar a 1 kHz.

La cantidad de ciclos de reloj necesarios para completar un período es: 

125.000.000 Hz / 1.000 Hz = 125.000 ciclos

Por lo tanto, el contador del PWM debía recorrer 125.000 ciclos de reloj para completar un período.

A partir de ese contador se compara su valor con el porcentaje de duty seleccionado.

La idea básica es: 

contador < límite del duty → PWM = 1
contador ≥ límite del duty → PWM = 0

¿Qué hace realmente el pwm.vhdl?

Una vez que el PWM básico estuvo funcionando, tuve que empezar a entender qué estaba haciendo realmente el código.

El archivo pwm.vhdl describe la lógica que implementa el PWM y el control mediante los botones.

El reloj y el contador

El proceso principal está sincronizado con el reloj mediante: 

if rising_edge(clk) then

Esto significa que la lógica se actualiza en cada flanco ascendente del reloj de 125 MHz.

Dentro de ese proceso existe un contador que avanza hasta alcanzar el valor correspondiente al período del PWM.

Para las tres frecuencias utilizadas: 

1 kHz → 125.000 ciclos
2 kHz →  62.500 ciclos
5 kHz →  25.000 ciclos

Cuando el contador alcanza el final del período vuelve a cero y comienza nuevamente.

El duty_select

Para controlar el duty utilicé una variable llamada duty_select.

No es un porcentaje almacenado como número decimal. Es simplemente un valor entero entre 0 y 10.

Valor Duty
0 0 %
1 10 %
2 20 %
5 50 %
10 100 %

Esto permite mantener el diseño relativamente sencillo y trabajar con pasos de 10 %.

La comparación que genera el PWM

La parte fundamental es la comparación entre el contador y el período. Conceptualmente, para un duty del 50 %, sería algo parecido a: 

counter < period * 5 / 10

Mientras esa condición se cumple, la salida está en nivel alto. Cuando deja de cumplirse, pasa a nivel bajo.

Así se obtiene la señal PWM.

FPGA y microprocesadores: una forma diferente de pensar

Una de las cosas que más me llamó la atención durante este proyecto fue la diferencia entre programar un microcontrolador y trabajar con una FPGA.

Cuando programamos un microprocesador normalmente pensamos en una secuencia de instrucciones: 

leer botón
↓
ejecutar código
↓
modificar una variable
↓
volver a empezar

En una FPGA la idea es diferente.

Con VHDL no estamos simplemente escribiendo una lista de instrucciones que un procesador va ejecutando. Estamos describiendo hardware digital.

En este proyecto, el contador está funcionando sincronizado con el reloj y la lógica de comparación determina continuamente el estado de la salida PWM.

No existe una instrucción que diga literalmente "generar PWM".

La descripción en VHDL termina convirtiéndose, después de la síntesis, en lógica digital dentro de la FPGA.

Esta fue una de las primeras cosas que tuve que cambiar en mi forma de pensar: una FPGA no es simplemente un microprocesador mucho más rápido.

Control mediante botones

El proyecto utiliza tres botones para controlar el funcionamiento:

Botón Función
BTN0 Aumentar duty
BTN1 Disminuir duty
BTN2 Cambiar frecuencia
BTN3 Reset

Para evitar que una pulsación mantenida cambie continuamente el valor, guardé el estado anterior de cada botón.

De esta manera puedo detectar el momento en que el botón pasa de 0 a 1, es decir, su flanco de subida.

En esta versión todavía no implementé un debounce específico. Eso queda como una mejora para una futura versión.

Antes de tocar la placa: simulación

Una de las cosas que aprendí durante este proyecto es que conviene no correr directamente hacia la placa cada vez que uno cambia una línea de VHDL.

Para eso está la simulación.

Preparé un testbench que genera el reloj y simula las pulsaciones de los botones.

El reloj utilizado en el testbench fue de: 

CLK_PERIOD = 8 ns

Esto representa correctamente el reloj real de 125 MHz de la Arty Z7.

Durante la simulación comprobé el cambio del duty y posteriormente el cambio entre las diferentes frecuencias.

Del simulador al hardware real

Una vez que la simulación parecía correcta llegó el momento de generar la síntesis, implementar el diseño y generar el bitstream para programar la FPGA.

Y ahí apareció una de las partes más interesantes del proyecto: que algo funcione en simulación no significa que automáticamente funcione en el mundo real.

Para sacar la señal PWM de la FPGA utilicé el conector Pmod JA.

La salida PWM fue asignada al primer pin del conector: 

Pmod JA1 → FPGA Y18

Desde allí fue posible observar la señal directamente con el osciloscopio.

El problema de BTN2

En determinado momento el PWM funcionaba, la simulación funcionaba y prácticamente todo parecía estar bien.

Excepto una cosa.

El botón para cambiar la frecuencia no hacía absolutamente nada.

Naturalmente, la primera reacción fue sospechar del VHDL.

Después de revisar el código y darle unas cuantas vueltas al asunto, resultó que el problema estaba en otro lugar: había asignado incorrectamente el pin del botón en el archivo XDC.

El BTN2 de la Arty Z7-10 está conectado al pin: 

BTN2 → L20

El pin que había utilizado anteriormente, M20, corresponde al switch SW0 de la placa.

Conclusión: la FPGA estaba bien. El que necesitaba debugging era yo.

Agregar control de frecuencia

Una vez solucionado el problema del botón, agregué la posibilidad de seleccionar tres frecuencias diferentes:

Selección Frecuencia Período en ciclos
0 1 kHz 125.000
1 2 kHz 62.500
2 5 kHz 25.000

Las cuentas son: 

1 kHz → 125 MHz / 1 kHz = 125.000
2 kHz → 125 MHz / 2 kHz = 62.500
5 kHz → 125 MHz / 5 kHz = 25.000

Con cada pulsación de BTN2 se cambia la frecuencia: 

1 kHz → 2 kHz → 5 kHz → 1 kHz

Finalmente comprobé las tres frecuencias directamente sobre el hardware y el funcionamiento fue correcto.

Mediciones con el osciloscopio

Una vez funcionando el sistema sobre la Arty Z7-10, medí la señal PWM con el osciloscopio.

Para la frecuencia de 1 kHz obtuve los siguientes resultados:

Duty seleccionado Duty medido Frecuencia
10 % 10,4 % 1,000 kHz
30 % 30,4 % 1,000 kHz
50 % 50,4 % 1,000 kHz
70 % 70,4 % 1,000 kHz
90 % 90,4 % 1,000 kHz

Las pequeñas diferencias entre el valor seleccionado y el valor medido pueden deberse a la resolución del contador y a la forma en que el osciloscopio determina el duty cycle.

Además de estas mediciones, comprobé físicamente el cambio de frecuencia entre 1 kHz, 2 kHz y 5 kHz, verificando que las tres opciones funcionaran correctamente.

¿Qué aprendí?

Que aprender FPGA es bastante más que escribir unas líneas de VHDL.

En este proyecto tuve que empezar a entender cómo trabajan conjuntamente el reloj, los contadores, la lógica secuencial, la simulación, la síntesis, la implementación, los constraints y finalmente el hardware.

También aprendí que hay una diferencia importante entre programar un microcontrolador y describir lógica para una FPGA.

Y aprendí algo todavía más importante: cuando algo funciona en simulación pero no funciona en la placa, no necesariamente hay que mirar el código durante tres horas seguidas.

A veces el problema está en el pin.

Y sí... eso también forma parte de aprender.
